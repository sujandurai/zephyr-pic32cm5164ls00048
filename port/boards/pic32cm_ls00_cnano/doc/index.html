📌 1. PIC32CM5164LS00048 SoC Overview

Purpose of the Document: This section focuses strictly on the SoC (System on Chip) layer in Zephyr RTOS, intentionally separating internal silicon-level initialization from general board-level wiring (LEDs, buttons, connectors).

  • Core Silicon Identity: Arm® Cortex®-M23 (ARMv8-M Baseline architecture) with hardware single-cycle multiplier, hardware divider, and ARM TrustZone-M security.
  • Role of the SoC Layer in Zephyr: Defines internal memory addresses, system oscillators, Phase-Locked Loops, power-level controllers, and memory protection (MPU/TrustZone) so that any board can instantiate this microcontroller without duplicating silicon setup code.

🕒 4. Clock Initialization

At cold boot, the device starts on the internal 16 MHz RC oscillator (OSC16M). The SoC initialization switches the MCU to full-speed 48 MHz operation via FDPLL96M at Performance Level 2 (PL2):

CLOCK GENERATION FLOW 
OSC16M (16 MHz Internal RC)
   ↓
GCLK1 (Generator 1 with Divide-by-16)
   ↓
1.0 MHz PLL Reference Clock
   ↓
FDPLL96M (Multiplier Ratio LDR = 47: 1 MHz × 48 = 48 MHz)
   ↓
48 MHz System Clock
   ↓
GCLK0 (Main System Clock Generator)
   ↓
CPU Core & Synchronous Bus (48 MHz)

Clock Step-by-Step Breakdown:

  1. Flash Wait States: Sets NVMCTRL_CTRLB.RWS = 2 (2 wait states) so Flash can be safely read at 48 MHz.
  2. Performance Level 2 (PL2): Transitions the Power Manager (PM->PM_PLCFG) to PL2 to enable maximum core frequency.
  3. OSC16M Setup: Configures OSC16M for 16 MHz calibrated output and enables it.
  4. GCLK1 Prescaler: Divides 16 MHz by 16 in GCLK1 to output a clean, ultra-stable 1.0 MHz reference clock.
  5. FDPLL Locking: Configures FDPLL96M channel with LDR = 47 (1.0 MHz × 48 = 48.0 MHz) and locks the PLL.
  6. GCLK0 Core Routing: Connects GCLK0 (main CPU clock) directly to FDPLL96M.
🗣️ What to Say in the Meeting / Viva:
“We deliberately implemented clock initialization at the SoC layer because the FDPLL96M ratio and PL2 power-mode transition are silicon-specific constraints. By driving GCLK0 at 48 MHz during low-level startup, every peripheral and Zephyr driver starts with stable timing.”

⚡ 5. soc_reset_hook() & Startup Sequence

The earliest execution point after hardware reset is soc_reset_hook(). It executes before any C runtime library or kernel variables are unpacked:

STARTUP SEQUENCE 
SRAM Initialization (Assembly Zeroing Loop)
   ↓
pic32cm_ls_clock_init()
   ↓
48 MHz Clock Locked (PL2)
   ↓
Zephyr Pre-Kernel Initialization (PRE_KERNEL_1)

SRAM ECC Clearing Range:

SRAM ZEROING BOUNDS 
0x20000000 (SRAM Base)
   ↓
[ 64 KiB Continuous Memory Zero-Init ]
   ↓
0x20010000 (SRAM Top)
💡 Implementation Rationale: On Cortex-M23 microcontrollers with Error Correction Code (ECC) or parity memory logic, uninitialized SRAM contains random floating states that cause false ECC traps upon first read. The 16-bit Thumb assembly loop in soc_reset_hook() clears all 64 KiB from 0x20000000 to 0x20010000, ensuring 100% stable cold-boot memory state.

📐 Important Zephyr Architectural Concept:
In Zephyr, peripheral hardware base addresses are never hardcoded inside device drivers. Instead, they are defined in pic32cm5164ls00048.dtsi and extracted at compile-time via DT_REG_ADDR() macros. This ensures complete portability across different SoC revisions.

🛡️ 7. ARM TrustZone-M Security Attribution

The Arm® Cortex®-M23 implements the ARMv8-M security architecture, dividing memory and peripherals into Secure and Non-Secure domains:

  • Secure vs Non-Secure Execution: Core boots in Secure state and partitions memory and peripherals via the Security Attribution Unit (SAU) and Implementation-Defined Attribution Unit (IDAU).
  • Peripheral Security Attribution: Peripheral Access Controllers (PAC) grant or block bus access based on the execution domain.
  • Correct Bring-Up Diagnosis: Ensuring all clock and power registers are accessible to Non-Secure applications without triggering HardFaults.
🗣️ How to Describe Issues During Bring-Up (Best Practice):
Say: “During bring-up, I had to distinguish clock-access problems from Secure/Non-Secure peripheral-access problems to ensure bus registers were properly attributed.”
Avoid saying: “TrustZone caused all my problems.”

⏱️ 8. 60-Second Meeting & Review Summary

A concise, ready-to-speak script covering the entire SoC port in 1 minute:

“To support the PIC32CM5164LS00048 in Zephyr, we established a structured SoC hierarchy following upstream RFC #92168, using PIC32CM GC00 and SG00 as reference blueprints.

📑 3. Deep-Dive: YAML Schemas (dts/bindings/)

  • Anatomy of a Devicetree Binding:
    • description: Documentation string describing the hardware peripheral.
    • compatible: Matches the node's compatible = "..." property (e.g. "atmel,sam0-gpio").
    • include: Inherits common property definitions from base schemas like gpio-controller.yaml or uart-controller.yaml.
    • properties: Defines allowed properties, data types (int, string, phandle-array), and whether they are required: true.
    • #cells specifiers: Defines how many cell integers follow a phandle reference (e.g. #gpio-cells: 2 for pin number + flags).
  • Point A — GPIO YAML (dts/bindings/gpio/atmel,sam0-gpio.yaml): 
    compatible: "atmel,sam0-gpio"

  - pin    # 0 to 31

  • Point B — UART YAML (dts/bindings/serial/atmel,sam0-uart.yaml): 
    compatible: "atmel,sam0-uart"

⚡ 4. Deep-Dive: DT-Bindings Headers (include/zephyr/dt-bindings/)

  • Why Dedicated DT-Bindings Headers Exist:

    Devicetree source files (.dts) are preprocessed with the C Preprocessor (cpp) before passing to the device tree compiler (dtc). Because DTS cannot parse C typedefs, structs, or function prototypes, headers in include/zephyr/dt-bindings/ contain pure preprocessor definitions (#define) and bitmask macros only.

  • Point A — zephyr/dt-bindings/gpio/gpio.h Flags: 
    #define GPIO_ACTIVE_LOW    (1 << 0)   /* Bit 0: 1 = Active-Low */
#define GPIO_ACTIVE_HIGH   (0 << 0)   /* Bit 0: 0 = Active-High */
#define GPIO_PULL_UP       (1 << 4)   /* Bit 4: Enable internal pull-up resistor */
#define GPIO_PULL_DOWN     (1 << 5)   /* Bit 5: Enable internal pull-down resistor */
#define GPIO_OPEN_DRAIN    (1 << 8)   /* Bit 8: Configure pin as Open Drain */
  • Point B — Usage in Board DTS:

    Because of gpio.h, instead of writing opaque numbers like gpios = <&porta 15 17>;, we write clean, human-readable declarations: 

    gpios = <&porta 15 (GPIO_ACTIVE_LOW | GPIO_PULL_UP)>;

Drivers in Zephyr RTOS — GPIO & UART Architecture

Point-by-Point Technical Reference: What is a Driver, Purpose in Zephyr, Reference Series (SAM0 & GC00), and Devicetree YAML Bindings

📌 1. What is a Driver in Zephyr?

  • Core Definition: A driver in Zephyr is a software module (written in C) that directly controls microcontroller hardware registers and exposes a standard, uniform programmatic API to the operating system and applications.
  • Hardware Register Abstraction: Eliminates low-level register manipulation (PORT_REGS, SERCOM_USART_REGS) from application code.
  • Standard Subsystem API Structures:
    • GPIO Driver API (struct gpio_driver_api): Function pointers for .pin_configure, .port_get_raw, .port_set_masked_raw, .port_set_bits_raw, .port_clear_bits_raw, and .port_toggle_bits.
    • UART Driver API (struct uart_driver_api): Function pointers for .poll_in, .poll_out, .err_check, and interrupt FIFO operations.
  • Static Compile-Time Instantiation: Uses DEVICE_DT_INST_DEFINE() to create const struct device instances in Flash ROM at build time (zero heap usage / no malloc).
  • One-Liner to Memorize:
    “Application code never touches hardware registers; it calls the generic Zephyr driver API, and the driver translates that call into microcontroller-specific register operations.”

🎯 2. What is the Purpose of Drivers in Zephyr?

  • Point 1 — Cross-Platform Portability: Application code (such as samples/basic/blinky and samples/hello_world) is 100% hardware-agnostic; the same C source runs unmodified on STM32, Nordic nRF, ESP32, and PIC32CM.
  • Point 2 — Decoupled Architecture Flow:
    DRIVER DATA FLOW
    Application Code (e.g., samples/basic/blinky)
   ↓ Calls: gpio_pin_toggle_dt(&led0)
Zephyr Subsystem API (zephyr/drivers/gpio.h)
   ↓ Invokes function pointer via struct gpio_driver_api
Hardware Device Driver (drivers/gpio/gpio_sam0.c)
   ↓ Writes bitmask to register
Physical Silicon Registers (PORTA.OUTTGL @ 0x4000301C)
   ↓ Toggles Yellow LED0 on Pin PA15
  • Point 3 — Compile-Time Hardware Safety: Validates peripheral base addresses, IRQ lines, and pin assignments at build time via Devicetree YAML schemas before code ever flashes to the MCU.
  • Point 4 — Deterministic Initialization Ordering: Priority levels (e.g. POST_KERNEL with CONFIG_GPIO_INIT_PRIORITY) guarantee system clocks (FDPLL96M 48MHz) and power domains are stabilized before peripherals initialize.

🔍 3. Which Series We Referred to for Creating / Reusing the Drivers

  • Reference 1 — Microchip SAM L10 / SAM L11 (SAM0 Series):
    • Shares the exact same Arm® Cortex®-M23 core with ARMv8-M TrustZone.
    • Shares the identical Port G1 GPIO controller and SERCOM peripheral register layouts.
  • Reference 2 — Microchip PIC32CM GC00 / SG00 Series:
    • Direct sister family in Zephyr sharing the identical Port G1 GPIO controller (PORT_REGS) and SERCOM USART bus architecture.
  • Reused Driver Files in Zephyr Tree:
    • drivers/gpio/gpio_sam0.c — Microchip Port G1 GPIO Driver.
    • drivers/serial/uart_sam0.c — Microchip SERCOM USART Driver.
    • drivers/flash/flash_sam0.c — Microchip NVMCTRL Flash Driver.
  • Why Driver Reuse Was Possible:
    • Microchip standardizes its Port G1 and SERCOM IP across both SAM0 and PIC32CM microcontrollers.
    • By declaring matching Devicetree compatible strings ("atmel,sam0-gpio", "atmel,sam0-uart"), we leveraged upstream-tested driver logic without writing new driver C code from scratch.
  • What to Say in Viva / Technical Reviews:
    “We did not need to write new GPIO and UART driver C code from scratch because Microchip standardized its Port G1 and SERCOM IP across SAM L10/L11 and PIC32CM. We reused Zephyr's upstream-tested gpio_sam0.c and uart_sam0.c, binding them to our SoC's memory addresses and IRQ lines via Devicetree.”

static int gpio_sam0_pin_configure(const struct device *port,
				   gpio_pin_t pin,
				   gpio_flags_t flags)
{
	const struct gpio_sam0_config *config = port->config;
	PortGroup *regs = config->regs;

	if ((flags & GPIO_OUTPUT) != 0) {
		regs->DIRSET.reg = BIT(pin);
	} else {
		regs->DIRCLR.reg = BIT(pin);
	}
	return 0;
}
